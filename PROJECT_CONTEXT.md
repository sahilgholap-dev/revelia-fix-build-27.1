## 1. What Revelia is

Revelia is an **AI-powered mystical reading mobile app**. Users get personalized readings generated by Claude (Anthropic) from their photos and birth data:

- **Face Reading** — upload a selfie; Claude Vision analyzes facial features → archetype, traits, strengths.
- **Palm Reading** — upload palm photo(s) (dominant / non-dominant hand) → palm type, lines, talents.
- **Astrology** — birth chart from date/time/place → daily insight, weekly forecast, monthly reading.
- **Numerology** — Pythagorean name + birth-date analysis → Expression / Soul Urge / Personality numbers, "Name Destiny" with optimized name variations.
- **Compatibility** — two people → relationship compatibility reading (love / friendship / etc).
- **Career Destiny** — synthesizes astrology + numerology + face + palm into career guidance.
- **Cosmic Blueprint** — a combined reading across modalities.
- **Ask the Stars** *(Build 27)* — a Q&A chat. Questions are classified by a router, answered against the user's own chart/numerology, and **date-bearing questions go through a deterministic Timing Engine** (Vedic dasha/transit rules) rather than being improvised by the model. Has explicit off-topic / unsafe / crisis handling. Per-tier monthly caps + an optional richer "Deep Insight" answer.
- **Personalized Cosmic Report** *(Build 27)* — a **Premium-Plus-only, 1/month**, asynchronously generated **17–26pp PDF** reading (tropical + Vedic sidereal astrology, full chart images, transits, numerology, own palm; deliberately **no face content**), delivered via a short-lived private link + email. Free users can view a shared sample.

Monetization is **subscription-based** (RevenueCat): Free / Premium / Premium Plus (Lifetime exists conceptually). Free tier gets limited readings; premium unlocks full readings, monthly astrology, Name Destiny, Career Path, etc.; Premium Plus additionally unlocks the Cosmic Report.

The app positions readings as **entertainment** (there's an explicit entertainment disclaimer + an "honesty preamble" baked into AI prompts to avoid harmful/over-confident claims). Safety matters here: the Q&A feature has a crisis path whose wording is signed off, and crisis screens deliberately suppress all upsell/paywall/rating surfaces.

## 5. Auth model

Three providers, all converging on a JWT issued by the backend:
- **Email + password + OTP** — signup requires email OTP verification. `/auth/verify-email` returns a `verificationToken` (**at the top level of the response body, not nested in `.data`**), which is then passed to `/auth/signup`.
- **Apple Sign-In** (iOS) — `fullName` only arrives on first sign-in (Apple privacy); backend handles that.
- **Google Sign-In** (Android) — requires the **Google Play app-signing SHA-1** registered in Google Cloud Console (not the debug keystore). The name is threaded from the mobile SDK to the backend (the Google tokeninfo endpoint doesn't return profile fields).

Every successful login path (email, Apple, Google) **and** `checkAuth()` (app-launch session restore) **and** `signup()` must call:
- `loginOneSignalUser(user._id)` — registers OneSignal external_id for push targeting.
- `identifyUser(user._id)` — RevenueCat identification.

Logout calls `logoutOneSignalUser()` + `logoutRevenueCat()`.

## 6. Subscriptions (RevenueCat)

- Mobile uses `react-native-purchases`. Offerings → `getOfferings()` returns a `PurchasesOfferings` collection; the paywall reads `offerings.current?.availablePackages` (NOT `offerings.availablePackages` — that's a past bug).
- Tiers: `free` / `premium` / `premium_plus`. `SubscriptionTier` type is in `mobile/lib/constants.ts`.
- **Build-27 gating notes**: the **Cosmic Report (R9) is Premium-Plus ONLY** (1/month; free *and* premium see the locked/upgrade state) — the mobile lock keys on the **server's `limit === 0`**, not on a tier name, so the server stays the single gate. Q&A (R7) has per-tier monthly question caps + a Deep-Insight sub-cap, enforced server-side in `qa-caps.service.ts`; over-cap returns a **top-level 402** (inside an otherwise nested-200 envelope).
- Backend persists tier via a RevenueCat webhook + **RTDN** (Real-Time Developer Notifications) wired through Google Cloud Pub/Sub → RevenueCat. The RTDN endpoint currently logs events and returns 200 (HMAC verification not yet added).
- **Complimentary tier grants**: backend supports comp grants for influencers — optional `User.subscription.comp` field + `getEffectiveTier(user)` utility (`server/src/utils/subscriptionTier.ts`) + a `grant-comp-tier.ts` admin script. For regular users (no comp), `getEffectiveTier` returns the normal billing tier — zero behavior change.
- RevenueCat billing only works on a **Play-signed build** (internal testing track or production), not on a bare APK.

## 7. Push notifications (OneSignal)

- `react-native-onesignal v5` is a TurboModule → **requires `newArchEnabled: true`**.
- The Expo config plugin must be **`onesignal-expo-plugin`** in `app.json` (NOT `react-native-onesignal` directly — v5.4.x ships no CJS-compatible plugin entry).
- Backend push scheduler: `server/src/jobs/pushScheduler.ts` (node-cron) sends a daily insight push + re-engagement pushes.
- OneSignal REST API: URL **`https://api.onesignal.com/notifications`**, auth header **`Authorization: Key <token>`** (NOT `Basic`). Server env var is **`ONESIGNAL_REST_API_KEY`**.
- Scheduler targets users by `external_id` (the MongoDB `_id`), which only works if `OneSignal.login(userId)` ran on-device — hence the login-path requirement above.
- **FCM does the actual delivery; OneSignal is just orchestration.** Two pieces are BOTH required: (1) a Firebase **service-account JSON** uploaded to OneSignal (FCM v1), and (2) a committed **`google-services.json`** baked into the build. Firebase lives in GCP project `revelia-497203`. **The Google Sign-In OAuth Web Client ID is unrelated to push** — Sign-In can work while FCM is entirely unconfigured (this exact gap meant push was silently never delivered until it was root-caused & fixed on 2026-06-24). Symptom of missing FCM: device shows "Unsubscribed / no push token" or "Invalid Google Project Number" even though sends report success. FCM uses NO env var — it relies on the committed file at build time.

## 8. AI / Claude usage

- All generation in `server/src/services/claude.service.ts`; per-surface model routing is single-sourced in `synthesis-routing.ts` (`createSynthesisMessage`). Current routing:

| Surface | Model |
|---|---|
| Marquee paid synthesis (monthly-premium, compat-premium, career, weekly) | `claude-fable-5` → `claude-opus-4-8` fallback |
| R9 Cosmic Report (`report` surface, `maxTokens` 96k) | `claude-fable-5` → `claude-opus-4-8` fallback |
| Daily / free-tier / validation | `claude-sonnet-4-6` |
| R7 Q&A — router/classifier | `claude-haiku-4-5` |
| R7 Q&A — free-tier answer | `claude-sonnet-5` |
| R7 Q&A — paid answer | `claude-opus-4-8` (explicit adaptive thinking) |
| R7 Q&A — Deep Insight | `claude-fable-5` (+ the same Opus fallback) |
| Geocoder | Haiku |

- **`SYNTHESIS_FABLE_ENABLED` is ON (`true`) in production** as of the 2.0.0 ship. The code default is OFF (unset ⇒ guaranteed Opus 4.8) — that default is the retention/availability safety net, distinct from the server-side `fallbacks` beta which only covers policy declines. Don't conflate the two.
- **R7 Q&A never asks the model for timing.** The `timing-engine.service.ts` produces the deterministic verdict/window from the rule set; the model only writes prose around it. Never suggest "let the model figure out the dates".
- **R9 is Mode B**: the backend computes every number (sidereal + tropical astronomy, dasha, transits, numerology, palm geometry) and injects it; Fable 5 writes interpretation *only*. A deterministic QA gate (page count 17–26, 12 section titles, zero em/en dashes, ≥3 chart images, **zero face-derived content**) must pass before a report can reach `ready`.
- Vision readings (face, palm, compatibility) fetch the image from R2, base64-encode, and send with the prompt.
- Retry logic: `withRetry()` wraps calls; `isRetryableError()` retries on `ECONNRESET`, `ETIMEDOUT`, `429`, `500`, `503`, `529` (Anthropic overloaded). The Anthropic client also uses `maxRetries: 4`.
- Truncation handling: responses are checked for `stop_reason === 'max_tokens'` and logged via `logAiFailure()`. JSON parsing goes through a hardened `safeJsonParse`.
- First-run vision readings can take 60–110s; server + mobile timeouts are set to ~180s.

## 9. Build & release pipeline

- Builds via **EAS Build**. Profiles in `mobile/eas.json`:
  - `preview` → APK, internal testing.
  - `production` → AAB, Play Store, `autoIncrement: true` (versionCode auto-increments per build).

- **The backend deploys from `server/Dockerfile`** (Railway build type flipped **Railpack → Docker** in Build 27, because the report renderer needs LibreOffice + python/matplotlib + fonts in the image). Node is pinned to 20. Anything the runtime needs at a path — e.g. the git-tracked hand-pose model weights under `server/assets/` — must be explicitly `COPY`-ed in the runtime stage or it silently 404s at runtime (this bit us once).
- TypeScript gate before any build: `cd mobile && npx tsc --noEmit` and `cd server && npx tsc --noEmit` — both currently clean. Plus the four committed server harnesses (§4).
- Release flow the team uses: build a versionCode → internal testing track → fix reported bugs → rebuild → re-test → promote to Play Store production.

## 11. Critical gotchas (non-obvious — easy to break)

1. **`newArchEnabled: true` must stay** — OneSignal v5 TurboModule crashes at import without it.
2. **OneSignal plugin = `onesignal-expo-plugin`**, not `react-native-onesignal` directly.
3. **OneSignal REST**: `https://api.onesignal.com/notifications`, `Authorization: Key <token>`.
4. **Env var names** (commonly confused):
   - Mobile: `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `EXPO_PUBLIC_REVENUECAT_ANDROID_KEY`, `EXPO_PUBLIC_ONESIGNAL_APP_ID`, `EXPO_PUBLIC_API_URL`.
   - Server: `GOOGLE_OAUTH_WEB_CLIENT_ID` (NOT `GOOGLE_CLIENT_ID`), `ONESIGNAL_REST_API_KEY` (NOT `ONESIGNAL_API_KEY`), `ANTHROPIC_API_KEY`.
5. **`verify-email.tsx`**: backend returns `verificationToken` at the **top level** of the body — read via `(verifyResponse as any).verificationToken`; do NOT change to `.data?.verificationToken` (always undefined → breaks signup).
6. **Paywall**: use `offerings.current?.availablePackages`, never `offerings.availablePackages`.
7. **`react-native-purchases` has no `codegenConfig`** — uses RN 0.79 old-arch interop. This is expected, not a bug.
8. **Rate limiting**: middleware uses `ipKeyGenerator(req.ip ?? '')` (express-rate-limit v7+ requirement).
9. **`app.set('trust proxy', 1)`** in `server/src/app.ts` is required on Railway, or rate limiting throws `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR`.
10. **`google-services.json` is tracked in git on purpose** — required for FCM; EAS only uploads git-tracked files, so re-ignoring it silently breaks Android push in the next build. Do not re-add to gitignore.
13. **Android push delivery = FCM**, needing BOTH a Firebase service-account JSON in OneSignal AND the committed `google-services.json`. Google Sign-In working ≠ FCM configured (they're independent). See §7.
11. **RevenueCat billing needs a Play-signed build** — won't work on a plain sideloaded APK.
12. **Google Sign-In needs the Play app-signing SHA-1** — debug keystore SHA-1 causes `DEVELOPER_ERROR`.

**Build-27 additions:**

14. **`app.json` `extra.apiUrl` BEATS the EAS profile env** — a build points at whatever backend `app.json` names, regardless of which EAS profile it was built with. This has already caused a real incident (an "internal" build silently talking to production). Always check `extra.apiUrl` before reasoning about which backend a build hits.
15. **The Timing Engine's rule set is GITIGNORED and loaded from private R2 at runtime**, not from the repo. So a deploy ships the new *engine* with the *old rules* unless the `rule-set.json` is re-uploaded to each environment's `revelia-timing` bucket. A green local `npm run test:timing` says **nothing** about deployed behaviour. Every rule amendment = commit the engine **AND** re-upload per environment; verify via the boot log's byte count.
16. **`versionCode` lives on EAS, not in `app.json`** (`appVersionSource: remote` + `autoIncrement`). The number in `app.json` is inert.
17. **The share helper returns a boolean.** `shareReadingCard` (`mobile/utils/shareReading.ts`) returns `true` for a real share, `false` for a dismissal, and passes `failOnCancel: false` to `RNShare.open`. Both look like dead complexity; both are the fix for an Android cancel-cascade (a dismissal otherwise rejected → the catch-driven fallback chain opened a second and third share sheet, and recorded a phantom share). Never "simplify" either away. Dismissal detection = the exported `isShareDismissal(error)`.
18. **In-app review has exactly one entry point** — `recordMeaningfulAction(key)` in `mobile/store/reviewStore.ts`, rehydrated once at launch by `initReviewStore()`. Do **not** add per-screen counters, fire-once refs, or direct `StoreReview` calls.
19. **Transactional emails carrying a signed/presigned URL must send with tracking OFF, per-send** — SendGrid click-tracking rewrites `<a href>` through a tracking subdomain that was never configured (NXDOMAIN) *and* can corrupt a presigned URL's signature. `EmailOptions.trackingSettings` is spread in only when present; only `sendReportEmail` sets it. Never change the global SendGrid account setting, and don't add it to the plain OTP/welcome sends.
20. **The Cosmic Report gate is server-side.** Mobile decides locked-vs-unlocked from the server's `limit === 0`, never from a tier name. Keep it that way when touching report UI.
21. **`astrology-sidereal.service.ts` owns its own `set_sid_mode`** (set-then-reset, internally). Callers — R7 and R9 both reuse it — must never re-issue it; doing so corrupts subsequent chart calculations.

## 12. Conventions

- Match the surrounding code's style; the project favors explicit, readable code over cleverness.
- Persistence on mobile uses **`expo-secure-store`** (not AsyncStorage for sensitive/flag data).
- Backend always returns a consistent shape conceptually (`{ success, data?, error?, message? }`) but **some endpoints put fields at the top level** (e.g. `verificationToken`) — don't assume everything is under `.data`.
- Shared types live in `packages/shared/types.ts`, imported in mobile as `@shared/types`.
- Commits: the team commits per logical change. **Branching**: feature work happens on `feature/build-NN` and merges to `main` when the build ships; **post-ship fixes go on `fix/build-NN.x` cut from `main`** (currently **`fix/build-27.1`** → releases 2.0.1, 2.0.2, …) — never back onto the already-shipped feature branch. Commit-message prefix follows the branch (`fix(build-27.1): …`).
- Every code change is gated on `npx tsc --noEmit` clean in **both** `mobile/` and `server/`, plus the committed server harnesses (`test:timing`, `test:qa-router`, `test:qa-prompt`, `test:qa-device-gate`) staying green.

## 13. How to give me the best help (for the web AI reading this)

When the user asks you to produce a **Claude Code prompt or plan**, aim for:
- **Specific file targets** when known (use the paths above), but instruct Claude Code to *verify* current contents first rather than assuming.
- **A clear definition of done** (e.g. "tsc clean on mobile and server", "no runtime behavior change", "works on Play-signed build").
- **Awareness of the gotchas in §11** — flag any that the task touches.
- **Respect the release flow** — the team builds a versionCode → internal testing track → fix reported bugs on the branch → rebuild (next versionCode, `autoIncrement`) → re-test → promote that same AAB to Play Store production. Don't suggest pushing straight to production.
- **Right-size to a point release.** The current branch (`fix/build-27.1`) ships **2.0.x** — minor fixes, UI polish, copy. If a request would need schema changes, a new AI surface, or broad refactors, say so and suggest it belongs in `feature/build-28` rather than quietly scoping it into a point release.
- **Remember there's no staging.** Anything server-side gets verified against the live production backend via Internal Testing. Plans that assume a safe pre-prod environment are wrong (§10).
- **Honesty about uncertainty** — if the task depends on exact current code you can't see, say "ask Claude Code to confirm X" instead of fabricating.

Good prompt shape for Claude Code:
> "On branch `feature/build-27`, in `<file>`, do `<change>`. Constraints: `<gotchas/conventions>`. Verify with `<command>`. Don't `<known pitfall>`. This is type-level-only / must be runtime-identical / etc."
