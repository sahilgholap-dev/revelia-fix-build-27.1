## 1. Goal & thesis
**Goal.** A flagship **paid, long-form PDF reading** (18–26 pages) generated by Fable 5, combining Western (tropical) + Vedic (sidereal) astrology, the full birth chart + transits, numerology, and palm reading, delivered as an in-app PDF + emailed secure link + share. One monthly generation for paid users; a fixed sample for everyone.
**Thesis.** This is the premium expression of the multi-modal moat — the depth artifact a generic app can't produce — and the **"generate for someone else"** path is the deliberate virality mechanic. It is independent of the R7 Timing Engine (the generation prompt excludes it), which is why R9 can ship before R7 completes.

## 2. Scope
### In scope (v1)
- Report content: Western + Vedic astrology, full chart + transits, **numerology**, **palm** (self only). Generated by **Fable 5** from Sid's prompt.
- **Placement in both** the Astrology tab (row under "Your Cosmic Blueprint") **and** the Explore tab (card). Indigo circular icon, gold crescent+star, gold **NEW** badge (not the purple PLUS badge).
- **Access model:** Free = sample only (Generate locked → upgrade). Premium & Premium Plus = **1 generation / month**, no rollover; one shared credit covers **self or someone-else** (not two pools).
- **Sample report:** one **static pre-generated PDF** (the Monty Adams sample), shown to every user first open; never generated on the fly.
- **Generate flow — two paths:** (a) **Self** — uses stored birth data + stored palm photo (no re-upload); full report incl. palm. (b) **Someone else** — typed name/DOB/TOB/POB; **astrology + numerology only, no palm** (deliberate BIPA/biometric call).
- **Delivery (all three, every generation):** automatic email with a secure download link; in-app PDF on a results page (highlights first, PDF below); native share-sheet button.
- **Results page** + report history/persistence.
- Push-notification copy (7 provided, §11).

### Out of scope (v1)
- **Face reading — HARD EXCLUSION.** The generation prompt supports a face layer, but Ani's spec forbids it: adding face triggers a Play Store policy reclassification (delist/relist). Do **not** wire the face layer even though the prompt has it.
- **Third-party palm** (BIPA exposure; typed data only for others).
- The **R7 Timing Engine** and all prashna/randomization (excluded from the generation prompt).
- Per-user teaser sample (the sample is static/shared).

## 3. Functional requirements
1. **Discovery:** cards/rows in both tabs with the specified icon + NEW badge; copy must convey astrology (Western+Vedic) + full chart + transits + numerology + palm, not just "dual-zodiac" (§11).
2. **Free user:** sees the static sample; "Generate Reading" is locked and routes to the upgrade flow. **No report is ever generated for a free user.**
3. **Paid entry screen:** shows remaining monthly credit ("1 credit remaining this month") + two buttons: **View Sample Reading** (opens static sample) and **Generate Reading**.
4. **Generate → choose self or someone-else** (§2). Self pulls stored birth data + palm photo; someone-else collects typed birth data, no palm.
5. **Generation is an async job** (see §4): tap → job enqueued → (minutes later) report ready → email + push + in-app results page. The UI must reflect an in-progress/queued/ready/failed state, not block on a synchronous request.
6. **Credit:** decremented on a **successful** generation (report produced + stored). Design the deduction like R7's discipline: a job that fails to produce a valid report does **not** consume the month's credit. One shared monthly credit for self-or-other. Reset: **see §6 open decision** (calendar month vs subscription renewal).
7. **Delivery triple** fires on completion (§7).
8. **Subject type:** if someone-else (or a self report where DOB implies a minor) is **under 18**, the generation must set `SUBJECT_TYPE=child` so the prompt's child rules apply (§9). **See §14 decision on whether child subjects are in v1.**
9. **Disclosures** on the report + in-app (§10).

## 4. Generation architecture (the core build question — SPIKE)
Sid's prompt runs two ways: **Mode A** (the model computes astronomy inline via `pyswisseph` and builds the .docx itself in a code-execution environment) or **Mode B** (the backend supplies a validated `ASTRONOMY_JSON` and the model consumes it). Production must decide how a 18–26pp PDF with computed astronomy + three matplotlib charts actually gets produced. Key facts and the decision Claude Code must resolve:

- **This is almost certainly a net-new pipeline.** Existing readings are likely LLM-text → in-app display, not 18–26pp PDFs. **Verify (§15)** whether *any* docx/PDF generation exists in the stack today.
- **It must be an async background job.** A Fable-5 report of this length takes minutes (R5 already flagged minutes-long Fable turns). It cannot be a synchronous HTTP request. Design: enqueue → worker generates → on completion, store PDF + fire email/push/in-app. Status states: queued / generating / ready / failed.
- **Two architecture candidates (Claude Code decides, grounded in infra + effort):**
  - **(B, recommended for data) Backend computes, model writes, renderer builds:** backend computes astronomy (the existing `sweph` engine — R7's spike proved it does Lahiri sidereal + dasha + transits by config, no license) and numerology (the shared util) deterministically, hands structured data to Fable 5, which returns the interpretive content; the document (docx→PDF + the 3 charts) is rendered by a controlled template. Most reliable, most control, biggest build. Keeps the model out of arithmetic (which the prompt itself insists on).
  - **(A) Model-generates-document via code execution:** if the backend/SDK supports Anthropic's code-execution + file tools, the model runs the prompt end to end (compute + docx + charts) as the prompt was written. Closest to Sid's artifact, least rendering code, least control over format/page-count/QA; **verify SDK/infra support for server-side code execution + file output.**
  - A hybrid is likely: backend supplies validated `ASTRONOMY_JSON` (Mode B) + numerology from the util; the doc rendering path is the open call.
- **Whichever path:** enforce the prompt's **QA gates** (page count 18–26, every Part/Appendix present, **zero em/en dashes**, images embedded, docx opens) before the report is marked ready and the credit is spent.
- **Cost/latency:** a full Fable-5 report is the most expensive single generation in the app; bounded by 1/month/paid-user. Log per-report cost + duration from day one (mirrors R7's week-one logging). Re-verify Fable pricing/limits via the `claude-api` skill.

## 5. Data sources (reuse, don't rebuild)
- **Astronomy:** reuse the R1 `sweph` engine at the prompt's fixed settings — Lahiri sidereal, whole-sign both zodiacs, mean node (true node footnoted), Moshier + speed flags, Vimshottari 365.25. R7's spike (GO) already proved these are reachable by config with no new libs / no `.se1` / no license. The report needs more than the natal snapshot: full **dasha ladder** (maha + antar), **transit ingress tables** (Saturn ~30y, Jupiter selected, Rahu), Sade Sati + returns, panchanga, navamsa (D9), dignities/yogas. Confirm which of these the engine already produces vs net-new (§15).
- **Numerology:** the shared util is the intended single source — **but see the Y-rule cross-link (§14-D1).** Recommendation: compute numerology **once via the shared util** and **inject** it into the report (rather than letting the model recompute), so the report and the app's Numerology tab can never disagree. This requires the util to expose all the report's fields (Pythagorean core, Chaldean, Vedic Mulank/Bhagyank, personal years) and to implement the agreed Y-rule.
- **Palm (self only):** pull the stored palm photo/observations; feed as the prompt's `PALM_OBSERVATIONS` structure or as images if the pipeline can see them. Enforce the prompt's hedging + biometric process-and-delete line.

## 6. Access, tiers & credit model
- Free = sample only; Premium/Premium Plus = 1/month shared (self-or-other), no rollover. Reuse `getEffectiveTier` + the existing counter/cron pattern (§15).
- **Deduction:** on successful, stored, QA-passed report only. Failed jobs don't spend the credit.
- **⚠️ Reset-boundary open decision (§14-D3):** the spec says "per calendar month, tied to subscription renewal" — those can differ. Recommend **calendar month** (UTC 1st) for consistency with the existing cron + R7 Q&A caps, unless PM wants renewal-date alignment.

## 7. Delivery
- **Email (secure link):** ⚠️ runs through the **same SendGrid integration that is currently broken** for Export My Data (UI succeeds, email never sends). **This gates a paid deliverable**, so it is a **blocking pre-ship fix**, recorded as a caveat now, fixed before R9 ships (§14-D5). A paid report silently not arriving is worse than a free export failing.
- **In-app:** results page, highlights first, full PDF viewable below.
- **Share:** native share sheet (WhatsApp, save to files, etc.).
- **Secure download links + PDF hosting:** generated PDFs need durable storage + secure, ideally expiring links. Confirm storage (S3 / Railway volume / existing bucket) and the link-signing approach (§15).

## 8. Data model & persistence
- **Report record** (per generation): subject (self | other), subject birth inputs (for other: typed name/DOB/TOB/POB), subject_type (adult|child), status (queued/generating/ready/failed), model + usage/cost, PDF storage key + secure link, highlights payload, timestamps, feedback (optional). Indexed by user.
- **Credit counter:** `user.report` sub-doc (or equivalent) — monthly count, reset by cron; designed for the shared self-or-other pool. Confirm shape (§15).
- **Sample asset:** the static sample PDF bundled/hosted + served to all users (confirm hosting, §15).
- **Third-party inputs:** stored per the report record; note privacy retention (typed birth data of a named third party) in the privacy posture.
- **Shared types:** any mobile-read DTO → `packages/shared/types.ts` (`@shared/types`).

## 9. Child subjects
The generation prompt has full **child rules** (`SUBJECT_TYPE=child`, under 18): domains become Mind/Temperament/Learning, Education timeline, gentle parent-facing health, Family/roots; **at most one adult-era partnership line; no fear-framed health; no destiny verdicts; face auto-skipped.** These are responsible and child-safety-aligned.
- **If child subjects are in v1 (§14-D4):** the "someone-else" flow (and a self report whose DOB implies a minor) must derive age from DOB and set `SUBJECT_TYPE=child`, and the pipeline must enforce the child rules. Never produce romantic/sexualized or fear-based content about a minor.
- **If deferred:** restrict v1 to adult subjects (block/skip when DOB implies under 18) — simpler and sidesteps the surface for launch.

## 10. Disclosures & legal
- Report + in-app entertainment disclaimer (the prompt's standing disclaimers: insight/entertainment; not medical/legal/financial; astrology contributes zero monetary figures; tendencies not verdicts).
- **Biometric:** palm images process-and-delete policy line (prompt Appendix D); palm photos stored securely, deletable from Profile.
- **Third-party palm exclusion rationale** (BIPA and comparable statutes) documented — typed data only for others.
- **No face** anywhere (Play Store constraint).
- Relationship/health content constrained per the prompt (no verdicts, structure/seasons only; health non-diagnostic).

## 14. OPEN DECISIONS (Sid / PM / Amey)
- **D1 — Numerology Y-rule, canonical method [Sid; spans R7 + R9] — RESOLVED: always-vowel, standardized project-wide.** Sid's decision: Y is **always treated as a vowel** across every numerology surface (app util, Q&A grounding, R9 report). Implementation: compute numerology **once in the shared util** (with the always-vowel rule) and **inject** the values into the report so the report and the app can never disagree; the R9 generation prompt's §4 line ("Y counts as a vowel when it is the only vowel sound in its syllable") is superseded by plain always-vowel and must be edited to match. Consequence: shipped Soul Urge / Personality numbers change for existing Y-name users across Complete Reading, Name Destiny, Career, and insights — requires a `NUMEROLOGY_VERSION` bump + one-time backfill (shared migration task with R7); affected users will see those two numbers shift once.

Determines the whole build shape. Recommend Mode B for data; doc-rendering path decided by the §15 spike.
